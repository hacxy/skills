# 技术博客写作指南

## 核心标准

好文章三个维度：**准确性 > 实用性 > 可读性**

- 代码能跑通，概念无误（底线）
- 读者看完能用，能解决实际问题
- 结构清晰，不需要反复重读

## 文章结构

### 万能五段式

| 部分 | 作用 | 占比 |
| ------ | ------ | ------ |
| 标题 | 回答"讲什么"，搜索友好 > 巧妙 | — |
| 引言 | 3 句话：写给谁？读完获得什么？ | ~10% |
| 背景/问题 | 为什么需要？解决什么痛点？ | ~15% |
| 核心内容 | 分步骤，每步有代码/示例/图解 | ~60% |
| 总结 | 核心 takeaway，不是重复全文 | ~10% |
| 参考资料 | 链接、进一步阅读 | ~5% |

### 渐进式披露

先讲大图（big picture），再逐步深入细节。不要一上来就甩 API 文档。

## 讲清技术概念：ADEPT 方法

| 步骤 | 含义 |
| ------ | ------ |
| **A — Analogy（类比）** | 它像什么？连接已知与未知 |
| **D — Diagram（图解）** | 用图激活另一半大脑 |
| **E — Example（示例）** | 让读者亲身体验 |
| **P — Plain-English（通俗描述）** | 用你自己的话说 |
| **T — Technical（技术描述）** | 最后才上术语 |

> 先体验，后定义。就像介绍一顿好饭：先让闻到香味、看到色泽，最后才说菜名。

## 可读性技巧

- **段落**：3-5 句为佳，长短交替
- **句子**：一个句子一个观点，避免 50 字以上长句
- **主动语态**："React 使用虚拟 DOM" 优于 "虚拟 DOM 被 React 使用"
- **第二人称**："你会遇到这个问题" 优于 "开发者可能会遇到"
- **加粗关键句**：每段第一句话或结论加粗
- **小标题密度**：每 200-300 字一个子标题
- **列表优于段落**：3 个以上要点时用列表
- **代码示例**：最小可运行，逐行注释，附上运行结果

## 去 AI 味

### 七大 AI 写作标志

| 标志 | 修复方法 |
| ------ | --------- |
| 套话填充词："值得注意的是"、"可以说" | 删掉，换成具体限定语 |
| 三连排比："快速、可靠、可扩展" | 改为两项或四项 |
| "不仅是 X，更是 Y" | 直接禁用这个句式 |
| 段落长度过于均匀 | 刻意合并短段、拆分长段 |
| 结尾总结段："总而言之" | 用一句具体的收尾 |
| 滥用破折号 | 每 300 字最多 1 个 |
| 模糊权威引用："研究表明" | 每个断言都要有具体来源 |

### 去 AI 味核心策略

1. 加入只有亲历者才知道的细节：踩过的坑、报错信息、开发环境
2. 承认不确定性："我不确定这是最佳方案，但它跑得很好"
3. 混合句子长度：偶尔来一句很短的。像这样。
4. 用口语化表达替代书面套话
5. 删掉一切不增加信息量的句子

## 口语化写作

### 核心：写给一个人看

- 用"你"而非"读者"、"开发者"
- 像跟同事聊天，不像写论文
- 允许不完美：可以用"嗯"、"说实话"、"坦白说"

### 技巧对照

| 书面版 | 口语版 |
| -------- | -------- |
| "在进行代码审查的过程中，我们发现了一个值得注意的问题" | "代码审查时我们发现了一个坑" |
| "接下来需要考虑性能优化" | "性能怎么办？" |
| "缓存是一种提高数据访问速度的技术" | "缓存就像你的书桌——常用的书放桌上，不用每次都跑书架" |
| "建议采用方案 A" | "我更倾向方案 A，因为..." |

### 读出声测试

把文章读出来。如果听起来像机器人在念稿，就改。

## SVG 图表使用

### 什么时候需要图

| 需要解释的 | 最佳图表类型 |
| ------------ | ------------- |
| 系统架构、服务关系 | 架构图 |
| 数据流、请求链路 | 流程图 |
| 算法步骤 | 流程图 |
| 组件关系 | 关系图 |
| 数据对比 | 表格 |

### SVG 优势

- 任意缩放不失真
- 搜索引擎和 LLM 可读（文字是真实文本）
- 版本控制友好（可以 diff）
- 文件小

### 设计原则

- 颜色对比清晰，确保可读性
- 添加 alt 文本说明
- 尺寸适配内容区域（建议宽度 600-800px）
- 简洁为主，避免过度装饰
